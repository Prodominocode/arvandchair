### ۱.۲ لایه‌ی Mock Data (`src/lib/mock-data/`)

یک فایل به‌ازای هر Collection سند ۰۲: `categories`, `products`, `pages`, `blog-posts`, `portfolio-projects`, `customers`, `orders`, `quote-requests`, `loyalty-tiers`, `loyalty-transactions`, `rewards`, `testimonials`, `site-settings` (+ `types.ts` مشترک). فقط Collectionهای مصرف‌شده در بسته‌ی ۱ (Categories/Products/PortfolioProjects/Testimonials/SiteSettings) واقعاً در UI این پیام دیده می‌شوند؛ بقیه (BlogPosts، Customers، Orders، QuoteRequests، Loyalty*، Pages) طبق دستور صریح شما از همین حالا ساخته شدند تا در بسته‌های بعدی فاز ۳ فقط مصرف شوند، نه ساخته.

**داده:** ۸ محصول واقعی روی هر ۵ دسته (۳ صندلی، ۲ میز، ۱ ست مبل، ۱ صندلی آمفی‌تئاتر، ۱ صندلی سالن همایش/سینما)، ۵ پروژه‌ی نمونه‌کار، ۵ توصیه‌نامه، ۴ پست وبلاگ، ۲ صفحه‌ی حقوقی، ۴ مشتری، ۲ سفارش، ۴ درخواست استعلام، ۳ سطح وفاداری، ۴ جایزه. همه‌ی فیلدهای 🌐 در هر ۲ زبان (fa/en) با ترجمه‌ی واقعی (نه ماشینی مستقیم بدون بازبینی، نه Placeholder) پر شده‌اند.

**تصمیم‌های گرفته‌شده حین ساخت Mock Data (نیاز به تأیید شما دارند):**

1. **Slug لاتین یکسان بین هر دو زبان.** `03-url-structure-seo.md` بخش ۵ صراحتاً می‌گوید تصمیم فارسی/لاتین‌بودن Slug فارسی هنوز باز است. برای اینکه فاز ۳ (UI/تست کلیک) معطل این تصمیم نماند، برای همه‌ی دسته‌ها/محصولات/پروژه‌ها یک Slug لاتین ساده و **یکسان در هر ۲ زبان** انتخاب شد (مثلاً `chairs`, `ara-managerial-chair`). این یک انتخاب موقت Mock است، نه حل آن تصمیم باز — وقتی تصمیم گرفته شد، فقط مقدار `slug` در همین فایل‌های Mock (و بعداً در Payload واقعی) عوض می‌شود.
2. **`salesMode` پیش‌فرض دسته‌های آمفی‌تئاتر/همایش-سینما = `quote-only`.** سند ۰۰ README «هنوز باز» این را عمداً به بعد موکول کرده بود؛ برای اینکه UI بسته‌ی ۱ (Badge/CTA محصول ویژه) چیزی برای نمایش داشته باشد، از همان توصیف خود سند ۰۲ («این دو دسته معمولاً پروژه‌محورند») به‌عنوان یک پیش‌فرض *موقت فقط برای Mock* استفاده شد — تصمیم نهایی همچنان باز و بدون تغییر مانده.
3. **لوگو همان JPG پس‌زمینه‌سفید فعلی** (`docs/assets/brand/arvand-logo.jpg` → کپی به `public/images/brand/`) بدون ویرایش استفاده شد؛ نیاز فنی باز سند ۰۶ (نسخه‌ی شفاف/وکتور) دست‌نخورده باقی مانده — چون Vectorize کردن لوگو کار فاز ۲/ورودی از کارفرماست، نه چیزی که در فاز ۳ حل شود.
4. **تصاویر placeholder به‌جای عکس واقعی محصول.** چون عکس/رندر واقعی محصولات هنوز وجود ندارد (و ساختن آن‌ها خارج از حیطه‌ی این فاز کدنویسی است)، ۱۴ آیکون SVG خط‌محور دست‌ساز در `public/images/mock/` ساخته شد (همان سبک `placeholder-3d.svg` فاز ۲: زمینه‌ی `surface-mist`، خطوط `arvand-slate`/`arvand-ink`) — یکی به‌ازای هر محصول/دسته/پروژه، به‌جای عکس Stock تصادفی یا جعبه‌ی خاکستری بی‌معنا. این‌ها آشکارا Placeholder ادعا نمی‌کنند عکس واقعی‌اند.
5. **همه‌ی توابع `lib/data/*` عمداً `async`** با اینکه Mock همگام است — چون در فاز ۵ فقط بدنه‌ی همین توابع به Payload Local API (که خودش async است) وصل می‌شود؛ هیچ Call-site ای در UI وقت سوییچ نیاز به تغییر ندارد.
6. **`resolveProductSalesMode()`** در `lib/data/products.ts` مقدار `inherit-from-category` را حل می‌کند (محصول → در نبود override، دسته را چک می‌کند → `mixed` در نبود override صریح محصول، برای امنیت به `direct-purchase` می‌افتد). این منطق چون در سند ۰۲ فقط به‌صورت متنی توضیح داده شده بود نه الگوریتم دقیق، اینجا برای اولین بار کدنویسی شد.

### ۱.۳ بسته‌ی ۱ — Layout + Home + About + Contact

**Layout عمومی (`src/components/layout/`):**
- `Header.tsx` (Server) + `HeaderNav.tsx` (Client) — لوگو، منوی دسکتاپ (`NavigationMenu` با Dropdown برای «محصولات»)، سوییچر زبان، آیکون سبد/حساب، CTA «درخواست استعلام»، و منوی موبایل (`Sheet`) با همان لینک‌ها.
- `Footer.tsx` (Server) — ستون‌های دسترسی سریع/دفاتر/شبکه‌ی اجتماعی/تماس + کپی‌رایت پویا.
- `LocaleSwitcher.tsx` (Client) — از `usePathname`/`Link` با `locale` prop next-intl استفاده می‌کند (بدون Dropdown پیچیده؛ چون حداکثر ۲ زبان داریم، لیست ساده‌ی Link کافی و در دسترس‌تر است).
- `[locale]/layout.tsx` بازنویسی شد: Header/Main/Footer/Toaster سراسری اضافه شدند؛ `isLocaleEnabled()` قبلی به `getEnabledLocales()` تبدیل شد (چون سوییچر زبان حالا حتی در صفحه‌ی فارسی هم باید بداند en فعال است یا نه). **نکته‌ی مهم برای مقاومت لوکال:** این فراخوانی به Payload داخل `try/catch` پیچیده شده — اگر دیتابیس موقتاً در دسترس نبود، فارسی هرگز نباید بشکند (طبق سیاست Local-First سند ۰۰)؛ در آن حالت فقط سوییچر en مخفی می‌شود، نه کل صفحه ۵۰۰.
- `Toaster` از `style-guide-content.tsx` به layout سراسری منتقل شد (یک‌بار mount، قابل‌استفاده از هر صفحه‌ای مثل فرم تماس)؛ `<main>` تکراری در `style-guide-content.tsx` به `<div>` تبدیل شد تا هر صفحه دقیقاً یک لندمارک `<main>` داشته باشد (از layout).

**⚠️ همان ناهماهنگی CLI فاز ۲ دوباره تکرار شد:** نصب `navigation-menu` و `sheet` با `pnpm dlx shadcn@latest add` باز هم `import { cn } from "cn"` نوشت (نه `@/lib/utils/cn`) — اصلاح شد. علاوه‌بر آن، `navigation-menu.tsx` فاقد دایرکتیو `"use client"` بود در حالی‌که از Context/State داخلی Radix استفاده می‌کند (بدون آن، رندر داخل یک Server Component مثل `Header.tsx` خطا می‌داد) — این یک باگ دیگر از رجیستری فعلی shadcn بود، دستی اضافه شد.

**صفحه‌ی اصلی (`/{locale}`):**
- Hero: از همان `Scene`/`SceneCanvas` فاز ۲ استفاده شد (بدون مدل محصول، چون هنوز glTF واقعی نداریم)؛ Fallback یک SVG برند جدید (`icon-hero-brand.svg`). دکمه‌ی اصلی «مشاهده‌ی محصولات» + ثانویه «درخواست استعلام».
- دسته‌بندی‌های شاخص (هر ۵ دسته)، محصولات ویژه (یک محصول از هر دسته — تنوع، نه صرفاً ۴ تای اول)، Portfolio منتخب (۳ پروژه‌ی `featured: true`)، CTA باشگاه مشتریان، بخش اعتماد (۳ توصیه‌نامه با ستاره).
- Structured Data: `Organization` JSON-LD طبق چک‌لیست سئو.
- `generateMetadata`: عنوان/توضیح از ترجمه + `canonical`/`hreflang` واقعی (کمک‌تابع جدید `lib/seo/metadata.ts`، توضیح در ۱.۴).
- **بدون GSAP/Framer Motion.** طبق سیاست `00-tech-stack.md` بخش ۲.۱ («قبل از افزودن هرکدام، بررسی کن آیا واقعاً لازم است»)، صفحه‌ی اصلی نیازی به روایت اسکرول‌بیس یا میکرو-اینترکشن پیچیده ندارد؛ فقط ترنزیشن‌های ساده‌ی Tailwind (سایه/هاور) استفاده شد.

**درباره‌ی ما (`/{locale}/about`):** تنها صفحه‌ی این بسته با GSAP واقعی — `gsap` نصب شد (`ScrollTrigger` از همان پکیج import می‌شود، بدون پکیج جدا). الگوی `reveal` از `lib/motion/scroll-tokens.ts` (فاز ۲) برای اولین‌بار مصرف شد: هر سکشن (Timeline، ارزش‌ها، تیم، CTA پایانی) با ورود به Viewport فید+اسلاید می‌شود. `gsap.matchMedia()` برای احترام به `prefers-reduced-motion` استفاده شد (نه فقط یک چک دستی؛ الگوی رسمی خود GSAP). منطق GSAP مستقیم داخل `about-content.tsx` نوشته شد، نه در `components/scroll/` — چون این اولین و تنها مصرف‌کننده‌ی این الگوی خاص است؛ استخراج به یک کامپوننت مشترک را به وقتی موکول کردم که یک صفحه‌ی دوم (مثلاً جزئیات محصول در بسته‌ی ۲) به همین الگو نیاز پیدا کند، تا انتزاع زودهنگام نباشد.

**تماس با ما (`/{locale}/contact`):** فرم تماس (نام/ایمیل/تلفن/شرکت اختیاری/پیام) کاملاً Client-side، بدون اتصال واقعی (طبق فاز ۳: «فقط UI و State»؛ اتصال به ایمیل تراکنشی/Mailhog کار فاز ۶ است) — Submit فعلاً یک `toast.success` نشان می‌دهد و فرم را ریست می‌کند. لیست شعب از `SiteSettings.offices` (Mock) با Structured Data `LocalBusiness` به‌ازای هر شعبه.

**نکته‌ی مهم درباره‌ی لینک‌های رو به جلو:** منوی Header/Footer و CTAهای صفحه‌ی اصلی عمداً به مسیرهایی مثل `/products`، `/portfolio`، `/quote-request`، `/loyalty-club`، `/cart`، `/account` لینک می‌دهند که هنوز ساخته نشده‌اند (بسته‌های ۲ تا ۵ همین فاز). این یک باگ نیست — طبق تصمیم شما («این فاز را در چند پیام جدا پیش می‌بریم»)، Layout و Home از روز اول باید نقشه‌ی کامل سایت را نشان دهند؛ این لینک‌ها با ساخته‌شدن بسته‌های بعدی به‌ترتیب ۴۰۴ دادن را متوقف می‌کنند. `/privacy-policy` و `/terms-of-service` (بسته‌ی ۶) هم همین‌طور.

### ۱.۴ کمک‌تابع سئوی پایه (`src/lib/seo/metadata.ts`)

چون سه صفحه‌ی این بسته همه به `canonical`/`hreflang` نیاز داشتند، یک تابع کوچک مشترک `buildAlternates(locale, pathname)` نوشته شد (به‌جای تکرار در هر صفحه) که از `getPathname()` خود next-intl استفاده می‌کند. **محدودیت آگاهانه:** چون دامنه‌ی نهایی هنوز مشخص نیست (فاز ۱۱)، این تابع فقط مسیر نسبی می‌سازد، نه URL مطلق — سخت‌سازی کامل سئو (URL مطلق، `metadataBase`، Structured Data بیشتر) طبق نقشه‌ی خودش کار فاز ۹ است؛ این فقط baseline لازم فاز ۳ را می‌دهد. هشدار بی‌ضرر Next.js درباره‌ی نبود `metadataBase` در لاگ dev دیده می‌شود و طبق همین تصمیم نادیده گرفته شد.

## بخش ۲ — تکمیل دامنه‌ی فعال فاز ۳ (بسته‌های ۲، ۳، ۶ + فرم استعلام قیمت)

**تاریخ:** ۲۰۲۶-۰۹-۲۲

بسته‌ی ۲ (کاتالوگ محصول)، بسته‌ی ۳ (Portfolio/وبلاگ)، و بسته‌ی ۶ (۴۰۴، حریم‌خصوصی/شرایط استفاده، Style Guide) مستقیماً توسط کارفرما ساخته شدند (خارج از این گفتگو — رجوع به کامیت‌های `main page...`, `improve hero section`, `add blog and portfolio singles and archives - add 404 page`)؛ جزئیات پیاده‌سازی آن‌ها در این گزارش ثبت نشده چون این Session در ساختشان دخالتی نداشت.

آخرین مورد باقی‌مانده از دامنه‌ی **فعال** فاز ۳ — یعنی همه‌چیز به‌جز بسته‌ی ۴ (سبد/Checkout/تأیید سفارش) و بسته‌ی ۵ (حساب‌کاربری/باشگاه) که آگاهانه موکول‌اند — فرم درخواست استعلام قیمت (#۱۶) بود که در همین Session ساخته شد:

- `src/app/(frontend)/[locale]/quote-request/page.tsx` + `quote-request-content.tsx`
- ورودی از دکمه‌ی «درخواست استعلام» صفحه‌ی جزئیات محصول (`ProductOverviewPanel.tsx` → `?product={slug}`) خوانده و با `getProductBySlug`/`getProducts` (`lib/data/products.ts`) به ردیف اول فرم Pre-fill می‌شود
- فرم چندآیتمی (محصول از `Select` + تعداد + توضیح اختیاری هر ردیف، امکان افزودن/حذف ردیف) + اطلاعات سازمان/تماس + پیام آزاد
- دقیقاً هم‌الگوی `contact/contact-content.tsx`: فقط UI و State (طبق قانون فاز ۳)، Submit یک Toast موفقیت نشان می‌دهد و فرم را ریست می‌کند — بدون اتصال واقعی به CRM/ایمیل (آن منطق فاز ۶ است)
- ترجمه‌های جدید: namespace `QuoteRequest` در `src/i18n/messages/{fa,en}.json`
- تست‌شده: `tsc`/`lint`/`build` سبز؛ تست زنده‌ی هر دو locale (`/quote-request`, `/en/quote-request`) و Pre-fill واقعی محصول از Query Param، هر دو ۲۰۰ و صحیح

## جمع‌بندی و قدم بعدی

با این مورد، **دامنه‌ی فعال فاز ۳ کامل شد** — تنها موارد باقی‌مانده در کل `05-pages-build-order.md` همان‌هایی هستند که آگاهانه به بعد موکول شدند (بسته‌ی ۴ به‌جز استعلام، و کل بسته‌ی ۵). قدم بعدی طبیعی طبق `01-workflow-roadmap.md`: یا فاز ۵ (اتصال داده‌ی واقعی) برای دامنه‌ی فینال‌شده‌ی فاز ۴‑الف، یا برگشت به طراحی UI بسته‌ی ۴/۵ برای باز کردن فاز ۴‑ب.
