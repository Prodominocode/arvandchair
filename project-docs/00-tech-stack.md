# ۰۰ | انتخاب Stack فنی

**پروژه:** پلتفرم فروش و معرفی محصولات مبلمان اداری (فروشگاهی + Portfolio + CRM + باشگاه مشتریان)
**نوع کار:** Vibe Coding با هوش مصنوعی — Stack باید یک‌ریپو (monorepo نه، بلکه single-repo)، تایپ‌سیف و کم‌اصطکاک باشد تا AI بتواند مرحله‌به‌مرحله و بدون گم‌کردن context پیش برود.

---

## ۱. تصمیم نهایی

| لایه | تکنولوژی | دلیل اصلی انتخاب |
|---|---|---|
| Framework اصلی | **Next.js 15 (App Router) + TypeScript** | SSR/SSG برای سئو، routing استاندارد و تمیز، پشتیبانی رسمی i18n، اکوسیستم بزرگ برای AI code-gen |
| CMS + Auth + API | **Payload CMS 3 (Embedded در Next.js)** | همان ریپو و همان سرور Next.js اجرا می‌شود؛ پنل مدیریت به‌صورت خودکار از روی اسکیمای TypeScript ساخته می‌شود؛ Auth، Access Control و Admin UI رایگان و آماده است — نیازی به ساخت پنل ادمین جدا نیست |
| دیتابیس | **PostgreSQL** (Payload Postgres Adapter) | داده‌های رابطه‌ای (سفارش ↔ مشتری ↔ محصول ↔ امتیاز وفاداری) به مدل رابطه‌ای نیاز دارد؛ برای CRM و گزارش‌گیری مناسب‌تر از NoSQL است |
| استایل | **Tailwind CSS v4 + shadcn/ui** | سرعت بالا در تولید UI با AI، اکسسیبیلیتی داخلی کامپوننت‌ها، سفارشی‌سازی کامل توکن‌های طراحی |
| موشن و اسکرول | **GSAP (ScrollTrigger) + Lenis (Smooth Scroll)** | استاندارد صنعتی برای روایت‌های اسکرول‌بیس (scrollytelling) و انیمیشن‌های پیچیده و کنترل‌شده |
| سه‌بعدی | **React Three Fiber + drei** | لایه React روی Three.js؛ برای نمایش سه‌بعدی محصولات مبلمان و صحنه‌ی Hero |
| میکرو-اینترکشن UI | **Framer Motion** | ترنزیشن کامپوننت‌ها، مودال‌ها، منوها — جدا از لایه‌ی روایت اسکرول (GSAP) |
| چندزبانگی | **next-intl** | Routing استاندارد مبتنی بر پیشوند locale (`/fa`, `/en`, `/ar`)، مدیریت رشته‌های ترجمه، سازگار با App Router |
| مدیریت State/Data | **TanStack Query + Zustand** | کش و همگام‌سازی داده‌ی سرور (سبد خرید، محصولات) + state سبک UI (منو، مودال، تم) |
| جستجو | **Meilisearch** (self-hosted) | جستجوی تایپ‌ای-هد چندزبانه، سریع، بدون هزینه‌ی بالای Algolia |
| پرداخت | **درگاه پرداخت بانکی ایرانی** (زرین‌پال/آیدی‌پی/زیبال/نکست‌پی — انتخاب نهایی طبق قرارداد PSP) | فروش فعلاً فقط داخل ایران است؛ Stripe به‌دلیل محدودیت‌های بین‌المللی برای کسب‌وکار ایرانی قابل‌استفاده نیست |
| ایمیل تراکنشی | **Resend** | تایید سفارش، خوش‌آمدگویی باشگاه مشتریان، بازیابی رمز عبور |
| ذخیره‌سازی مدیا | **Cloudflare R2** | سازگار با S3 API، ارزان، بدون هزینه‌ی Egress |
| هاست | **Vercel** (اپ Next.js) + **Neon/Supabase** (Postgres) | Deploy سریع، Preview Deployments برای هر مرحله از کار AI |
| مانیتورینگ خطا | **Sentry** | لازم برای فاز CRM/پرداخت که خطا در آن‌ها هزینه‌بر است |

> **به‌روزرسانی فاز ۰ (تعیین‌شده):** فروش آنلاین فعلاً فقط داخل ایران است (بدون صادرات فعلی). زبان عربی سایت **ارتباطی به جغرافیای فروش ندارد** — صرفاً پوشش محتوایی/مخاطب است؛ Checkout و حمل‌ونقل فقط برای آدرس داخل ایران فعال می‌شود.
>
> **نکته‌ی عملیاتی مهم که باید قبل از فاز ۱ بررسی شود:** چون کسب‌وکار ایرانی است، باید تأیید شود که سرویس‌های خارجیِ این Stack — Vercel، Neon/Supabase، Cloudflare R2، Resend، Sentry — بدون محدودیت برای یک شرکت ثبت‌شده در ایران قابل‌استفاده و پایدار هستند، یا باید جایگزین داخلی/منطقه‌ای برای هرکدام در نظر گرفته شود. درگاه پرداخت هم قطعاً باید ایرانی و دارای مجوز (اینماد + قرارداد PSP) باشد.

## ۲. چرا این ترکیب برای Vibe Coding مناسب است؟

1. **تک‌ریپو، تک‌سرور:** Payload به‌صورت Embedded داخل Next.js اجرا می‌شود، یعنی AI مجبور نیست هم‌زمان دو پروژه‌ی جدا (بک‌اند و فرانت) را مدیریت کند و context را از دست ندهد.
2. **اسکیمای TypeScript = مستند زنده:** تعریف هر Collection در Payload هم مدل داده است، هم مستند، هم پنل ادمین. برای AI که قدم‌به‌قدم پیش می‌رود، این یعنی کمترین حدس‌زدن.
3. **Type Safety سرتاسری:** از دیتابیس تا کامپوننت React، تایپ‌ها به‌صورت خودکار تولید می‌شوند → خطاهای رایج AI-generated code (اسم فیلد اشتباه، شکل داده‌ی نادرست) در Compile Time گرفته می‌شود.
4. **URL و SEO استاندارد به‌صورت پیش‌فرض:** App Router + next-intl یعنی ساختار URL تمیز و چندزبانه از روز اول درست تعریف می‌شود، نه اینکه بعداً Refactor شود.
5. **جداسازی لایه‌ی موشن:** GSAP برای روایت اسکرول، Framer Motion برای تعامل UI — تداخل و شلوغی کد جلوگیری می‌شود.

## ۲.۱ سیاست استفاده از کتابخانه‌های موشن/سه‌بعدی (مهم — محدودیت وابستگی)

**تصمیم:** هیچ‌کدام از سه کتابخانه‌ی GSAP+ScrollTrigger+Lenis، Framer Motion، و React Three Fiber+drei نباید به‌صورت Global و روی همه‌ی صفحات لود/استفاده شوند. هرکدام فقط **دقیقاً همان‌جایی که کارکرد را بهتر می‌کند** به‌کار می‌رود، به‌صورت Lazy-load و مجزا از هم.

**اولویت و میزان استفاده (از بیشترین به کمترین):**

| کتابخانه | نقش | میزان استفاده |
|---|---|---|
| **GSAP (ScrollTrigger) + Lenis** | ابزار اصلی و غالب پروژه برای روایت اسکرول (Scrollytelling)، پین‌شدن بخش‌ها، ترنزیشن بین سکشن‌ها | بیشترین — در بیشترین تعداد صفحه (Home، About، جزئیات محصول، Portfolio) |
| **Framer Motion** | فقط برای میکرو-اینترکشن‌های UI مبتنی بر رویداد کاربر (باز/بسته‌شدن منو و مودال، تأیید افزودن به سبد، Toast) | متوسط — محدود به کامپوننت‌های تعاملی مشخص، نه سکشن‌های صفحه |
| **React Three Fiber + drei** | فقط برای صحنه‌ی Hero برند و Viewer سه‌بعدی محصول (اگر مدل glTF موجود باشد) | کمترین — حداکثر ۲ الی ۳ نقطه‌ی مشخص در کل سایت، همیشه با Fallback سبک برای موبایل |

**قواعد اجرایی برای AI:**
- قبل از افزودن هرکدام از این سه کتابخانه به یک صفحه/کامپوننت جدید، اول بررسی کن آیا واقعاً لازم است یا با CSS Transition ساده/Tailwind قابل انجام است.
- Import این کتابخانه‌ها همیشه Dynamic و محدود به همان کامپوننت باشد؛ هرگز در `layout.tsx` سراسری import نشوند.
- اگر صفحه‌ای نیاز به هیچ‌کدام ندارد، هیچ‌کدام اضافه نشود — «مدرن بودن» به معنای استفاده‌ی همه‌جا نیست.

## ۳. گزینه‌های بررسی‌شده و رد شده

| گزینه | چرا رد شد |
|---|---|
| **Strapi / Sanity** به‌جای Payload | جدا از اپ Next.js اجرا می‌شوند (دو سرویس، دو Deploy) → پیچیدگی بیشتر برای مرحله‌به‌مرحله پیش‌رفتن با AI |
| **WordPress + WooCommerce** | برای UI سه‌بعدی/اسکرول‌بیس مدرن و ساختار کد تایپ‌سیف مناسب نیست؛ سرعت توسعه با AI پایین‌تر |
| **Nuxt (Vue)** به‌جای Next.js | اکوسیستم کتابخانه‌های سه‌بعدی/اسکرول (R3F، Framer Motion) در React قوی‌تر و به‌روزتر است |
| **MongoDB** به‌جای Postgres | داده‌ی CRM/سفارش/وفاداری رابطه‌ای است؛ گزارش‌گیری SQL ساده‌تر و قابل‌اعتمادتر |
| **Shopify** به‌عنوان کل پلتفرم | برای CRM سفارشی و باشگاه مشتریان اختصاصی محدودیت دارد؛ کنترل کامل روی UI سه‌بعدی سخت‌تر می‌شود |

## ۵. ساختار پیشنهادی پروژه (ریشه‌ی ریپو)

```
/src
  /app
    /(frontend)
      /[locale]
        /page.tsx                → صفحه‌ی اصلی
        /products/...
        /portfolio/...
        /blog/...
        /account/...
        /cart, /checkout
        /auth/...
    /(payload)                   → مسیرهای ادمین/API که Payload می‌سازد
  /collections                   → تعریف مدل‌های داده (Products, Orders, Customers, ...)
  /components
    /ui                          → کامپوننت‌های shadcn
    /scroll                      → کامپوننت‌های GSAP/ScrollTrigger
    /three                       → صحنه‌های R3F
  /lib
    /data                         → لایه‌ی Data Access (فاز ۳: از mock-data می‌خواند، فاز ۵: از Payload می‌خواند)
    /mock-data                    → داده‌ی نمونه‌ی TypeScript برای فاز ۳ (قبل از نهایی‌شدن Schema)
    /payload-client, /payment-gateway, /meilisearch, /utils
  /i18n                          → فایل‌های next-intl و رشته‌های ترجمه
  /styles
/docs
  /progress                      → گزارش پیشرفت هر فاز (طبق سند ۰۱-Workflow)
/public
```
